# Skill Improve｜技能改进

创建 Skill 时，强模型可能靠自己的推理和开发聊天补齐了说明中的空白。换个模型、开个新对话，这些未写下来的方法就容易丢失。

Skill Improve 在 Skill 创建和后续改进过程中补全方法：创建流程产出草稿后、交付前检查关键遗漏，后续优化时继续补齐有依据的步骤、判断条件、质量标准和例子，并按实际执行条件验证。它保留必要细节和合理自主空间，帮助使用者减少猜测作者意思的负担。

## 开始使用

需要一个能读取技能文件的 Agent。改进已有技能时提供完整包；从零创建时先提供目标和材料，由创建流程产出初稿，再由本 Skill 在草稿交付前检查。宿主能写文件时可直接生成改后包；只能读取时可返回完整候选文本或补丁，由你保存。本项目本身没有必须安装的运行时、服务或付费接口；真正的模型实测需要宿主支持指定配置，并可能产生该宿主的调用费用。

以 Codex 为例，在希望使用它的项目根目录运行以下命令，需要已安装 Git。它只把完整包放入当前项目的技能目录；已有同名目录时，先按[更新说明](docs/integration.md)处理。

```sh
git clone https://github.com/Ww-Cooooo/skill-improve.git .agents/skills/skill-improve
```

也可从[仓库](https://github.com/Ww-Cooooo/skill-improve)下载 ZIP，把解压出的完整目录命名为 skill-improve，放到项目的 .agents/skills/ 下。保留 references、assets、agents 等子目录，确认最终路径是 .agents/skills/skill-improve/SKILL.md，没有多套一层目录。

在该项目中新建会话，确认技能列表能找到 skill-improve。提供目标包的位置或附件，或说明要创建什么技能。改进已有包的例子：

> 使用 $skill-improve 改进这个已有 Skill。未来由我指定的模型和思考档位执行，请先读取完整包及我提供的开发记录，补齐影响独立执行的遗漏，保留原意。对话汇报简洁，技能文件需要的细节写充分。把修改后的包和验证记录放到我指定的输出目录。

创建新技能时也可明确提出：“使用 skill-creator 创建这个 Skill，并在草稿交付前使用 Skill Improve 检查方法与独立执行条件。”没有点名时，主动介入规则同样适用，实际选择由宿主和 Agent 完成。

没有技能发现机制的宿主，也可保留完整包，直接请求“读取 [本包目录]/SKILL.md，按其中流程改进 [目标技能目录]”。把方括号内容替换为真实路径；这种手动读入不依赖宿主识别 $skill-improve，也不代表自动触发已经可用。

最好同时说明未来模型和档位、宿主及工具，并提供已有的成功或失败产物。信息不足时先处理能确定的部分；缺少真正影响改法或实测配置的信息才询问。

你会得到修改后的技能包或可应用的补丁，以及需要时的代表性成果和验证说明。未指定输出位置时，按所在项目约定保留可恢复的原包和修改结果。没有项目约定时，请在请求中指定一个目录，例如项目内的 skill-improve-output/，让结果容易找到。

## 它怎样补全 Skill

| 检查的问题 | 采取的行动 |
| --- | --- |
| 重要方法只留在开发聊天里 | 从获准使用的材料中恢复定义、条件和经验，写进可交付包 |
| 说明存在，但模型不知道如何使用 | 修正触发、引用和读取时机，补充有区分度的例子 |
| 原模型成功，换模型或新任务失败 | 使用真实目标配置和独立上下文检查，必要时比较新旧包 |
| 步骤齐全，成果仍然不好 | 检查实际作品，区分说明、方法、工具与能力问题 |
| 资料只在作者电脑或私人环境里 | 整理包内资源和明确依赖，保留必要条件与适用边界 |

改进时可以利用已有开发背景；验证改后包时，执行者不应得到额外的开发答案。正常业务输入、工具和系统规则仍然保留。

## 与 skill-creator 的关系

由 skill-creator 等创建流程主导初稿；Skill Improve 在草稿形成后、交付前检查方法是否交代充分，之后也可改进已有包。创建工具已经做过且仍适用的编写、结构检查和评测结果可以复用。

Skill Improve 本身有完整改进流程，不强制安装某一家创建工具。它处理已有包的具体执行缺口，避免为每次小修改重建一套开发流程。

## 什么时候主动使用

宿主已发现本 Skill 时，Agent 应在创建、实质修改、优化技能或适配新执行模型的工作中主动使用它，包括任务中途才进入这些工作，不必等待你点名。普通业务调用、纯安装和错字小修不启动完整改进流程。

主动使用不等于每次重跑全部测试。同一轮工作复用已完成检查，也不让它和创建工具反复互相调用。仅在业务运行中发现问题，不自动授权修改全局技能。

包内已允许隐式调用，名称和描述会告诉 Agent 何时适用。实际选择仍依赖宿主的发现与调度能力；自动触发是否可靠，需要在实际宿主中验证。

希望把检查接到项目的创建流程中，可选用[项目接入说明](docs/integration.md)和[规则片段](assets/agents-snippet.md)：把片段合并到该项目已有的 AGENTS.md，在草稿交付前提醒 Agent 使用本 Skill。安装不自动修改规则，规则也不保证每次选择成功。全项目个人安装、其他宿主、未触发时的排查也见接入说明。

## 验证与适用范围

检查格式、作者自测、目标模型独立执行和迁移对照是不同证据。无法调用目标模型时，会交付已完成的改进并标出未验证范围；不会以“扮演目标模型”代替实际运行。

项目的本次验证范围见 [验证记录](docs/validation.md)，要求落实位置见 [设计要求对应表](docs/requirements.md)。包内示例均为明确标注的虚构材料，不代表真实用户数据或已证明的普遍效果。

这是可由支持文件型技能的宿主读取的说明包。具体模型与宿主能否达到目标质量，需要在对应条件下核实；当前记录没有覆盖的环境属于未验证。

## 文件与数据

Agent 会读取你提供的目标包、获准使用的开发材料及成果；宿主可写时在约定位置保存修改和测试输出，只读时返回候选内容供你保存。向模型发送这些材料的方式由所在宿主决定；本项目不附带上传器或后台服务。

改进请求不自动授权公开聊天、发布仓库、安装工具或同步全部技能。原始私人材料不应进入公开分发包；失败证据和原包按任务需要保留。
