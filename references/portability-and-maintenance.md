# 独立使用与维护

公开分发、检查环境依赖、触发范围、长期使用边界或变更后验证时读取。目标是交付完整可理解的技能包，不是承诺所有模型与平台都兼容。

## 能独立使用需要哪些条件

独立性指不依赖作者的隐藏背景。用户正常提供的业务材料和已声明工具仍然可以是必要输入。

逐项核对：
- SKILL.md 提到的包内文件存在，路径按包位置解析；安装和交接需要复制完整包。
- 私人绝对路径转换为相对资源或由使用者明确提供的位置。用户有意设计的环境专用路径可配置并说明，不强制全平台兼容。
- 工具、运行时、接口和资源的必要性明确；确有版本约束时说明适用版本和核查方式。
- 外部资料的来源和读取时机明确。缺少联网时会影响什么，能够继续什么，要有真实边界。
- 另一个 Skill 只有确实必要且目标宿主可获得时才作为必需依赖；不能只写“使用之前那个 Skill”。
- 可选依赖缺失不阻塞无关步骤。必要依赖缺失时，停止对应不可靠操作，说明可提供的部分成果。
- 当前用户要求可以覆盖默认参数，宿主更高优先级指令和实际权限继续有效。

不要把自己的工具列表写成所有宿主必然具备的能力。测试中模拟了某工具时，结果只证明那种条件下的行为，不能声称真实工具可用。

## 检查触发与边界

名称和描述帮助宿主决定是否读取正文。创建、实质改进及工作中途进入这些阶段的条件要写进入口 description，不能只藏在尚未加载的正文。围绕真实任务写，避免用“处理一切”“所有优化”招来无关请求。agents/openai.yaml 明确允许隐式调用；其他宿主是否读取该配置需单独核实。

按需要检查：
1. 用户直接点名，能否读取正确入口。
2. 用户只描述实际问题，是否适用。
3. 用户原始请求未提 Skill，但获准工作中途出现技能创建或实质改进时，能否进入对应阶段。
4. 创建草稿已有时，能否在交付前检查交接，并复用创建者已有证据；还没有草稿时，能否让创建流程先产出草稿。
5. 普通业务、纯安装或错字小修能否继续原流程，避免不必要的改写和评测。
6. 同一流程已加载时是否继续当前步骤，避免自调用或与创建工具相互循环。
7. 目标是已有包却没有提供位置时，能否询问其位置，或明确只提供候选而非声称已应用。

典型正例包括“这个技能换模型后表现差”“为新写好的 Skill 检查交接”以及“工作中决定将已获准沉淀的方法写成 Skill”。从零创建应纳入后续草稿检查，不能用“没有草稿”排除整条创建工作流。典型负例是“直接用这个技能完成业务任务”“复制安装这个包”“把 README 的错字改掉”；负例不代表禁止相关小修，而是不扩大成完整改进评测。

测试不要只用含有名字或关键词的用户请求，还要提供合理的中途工作状态，观察 Agent 是否在相应阶段读取本包、做必要检查并继续交付。给出入口元数据的选择题只能检查描述理解；手动要求读全文只能检查读后行为。这两种证据都不能替代真实宿主的发现、选择和执行记录。若用户需要必经检查，应在其选定且获准修改的创建工作流中设置交付检查点；本 Skill 不私自修改全局指令或其他创建工具来强制触发。

发现问题要分层定位：入口未暴露给 Agent，先修安装目录、启用状态或宿主列表限制；入口可见却未选择，检查真实任务与描述、同名副本和调用策略；已读却不会用，回到方法与行为诊断。不要把所有未触发都归咎于 description，也不要通过扩大到所有任务来提高表面触发率。

需要安装、项目工作流接入或故障排查时，读取 [接入说明](../docs/integration.md)。其中 [项目规则片段](../assets/agents-snippet.md) 是使用者可选合并的资源，不自动生效，不是本 Skill 日常执行时的必读文件。让入口在工作开始时可见，比只在正文重复“必须调用”更有用；实际加载和执行仍需宿主证据。

## 公开包需要保留什么

保留使方法成立的条件、理由、完整示例、必要素材或明确的素材输入约定。把公开包缩成口号不能获得独立性。

发布前区分：
- 可公开的通用方法。
- 用户自己的偏好与品牌规则；仅在产品本来服务这些约束时保留并解释。
- 个人、客户或商业资料；没有公开授权时不直接携带。
- 密钥、令牌、Cookie、登录态和本机缓存；不进入分发包。
- 第三方代码与资源；保留相应来源及许可证，不把自有许可证套在没有权利的材料上。

改进请求本身不等于发布授权。许可证选择、仓库公开、上传材料等按用户实际授权进行；有明确开放许可时保留，不擅自替换。使用虚构案例时标明虚构，不能把它们包装成真实成功案例。

包中的 SOURCES 或来源记录用于追溯设计依据，不能代替本包效果证据。普通用户不应为了第一次使用而读完作者审查记录。

## 与创建工具配合

用户可用 skill-creator 或其他工具主导创建，本 Skill 在草稿形成后、交付前主动查漏，也可以在原对话中改进已有包。创建工具可能具备评测能力；可复用现成工具和结果，但要核对其上下文、模型及版本是否满足这次结论。

本 Skill 不强制另装某一家创建工具。若宿主可用的创建工具适合本次结构或脚本改动，读取它的相关说明；若不可用，按本包规则继续，并只报告实际缺少的功能。不要建立循环调用，让两个技能反复要求对方完成同一个任务。

## 维护和升级

维护由用户当前请求或明确授权的自动化触发，本文件不是后台程序。修改范围围绕实际问题，不遍历并更新用户所有技能。

每轮：
- 保留原包和有效局部改动；应用前核对修改的版本。
- 记录影响行为的实际变更。普通小修无需发布一套报告。
- 修改公共入口或核心判断时，检查相关触发与任务；修改特定分支时检查相应分支。
- 记录本次被验证的配置和范围；新模型、新工具或不同宿主的兼容性不能由旧记录自动继承。
- 区分源文件更新、安装副本更新、现有会话是否重载。不能控制重载就说明需要新会话或宿主刷新，不声称已清除隐藏状态。

交付以用户任务是否完成、质量是否达到要求、实际成本是否合适为依据，不以字数、文件数或检查次数为完成标准。
