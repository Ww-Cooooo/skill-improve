# 独立验证

安排行为测试、比较新旧版本或给出“有效”“已适配”结论前读取。测试对象是一个完整技能包在某种执行条件下的行为；单独测试提示词片段、静态脚本或模型问答不能代表所有使用场景。

## 先定义要证明什么

将本轮问题转成少量会改变结论的检查。比如：能否依据提供资料保留事实、按已声明定义统计、产出可打开的文件、遇到缺失输入时合理询问。关键质量标准在运行前确定，不能看完结果后偷偷降低标准。

分别看：
- 方法本身是否有可接受的成果依据。
- 独立执行者是否获得了完成任务所需的信息。
- 真实行为和实际成果是否符合业务目标。
- 相对旧版或无 Skill 的改善是否值得额外时间和成本。

固定字段、数字与文件行为可直接核查；创作质量需要参照和具体描述。不得用标题数量、回复长度或“我完成了”的自述替代成果检查。

## 测试执行配置必须是真的

记录计划模型、计划思考档位、宿主及相关工具。确认宿主实际支持这些配置，并通过调用参数、会话元数据或可获得的运行记录确认采用了什么。

说明证据层次：
- 请求参数能证明“请求了此配置”。
- 宿主返回的会话元数据能证明“宿主记录为此配置”。
- 若存在服务端响应的模型标识，可补充记录。
- 无法取得更深层路由信息时，明确限制，不由模型自报身份或执行速度倒推型号。

不要为了取得配置证明读取凭据或扩大日志访问。没有目标型号或档位时，不能默认用创建者型号替代；用户允许替代则单独标注，结果不自动外推回原配置。让模型“扮演某型号”无效。

区分“运行 Skill Improve 的维护模型”和“执行被改进 Skill 的目标模型”。前者可以利用开发资料，后者的独立测试不能借此获得额外信息。测试本 Skill 时，也要说明是在验证维护流程，还是在验证改后目标包的业务效果。

## 建立可说明范围的隔离

新建没有开发聊天历史的会话，或使用明确不继承历史的执行方式。新 Agent、不同名字、清空页面或一句“忽略之前内容”，都不能自动证明隔离。

执行者可获得：
- 冻结的完整待测技能包。
- 普通用户会提供的业务任务与原始材料。
- 正常运行必需的系统规则、工具及环境说明。
- 安全执行边界和输出位置。

执行者不能提前获得：
- 创建聊天、维护诊断、拟修方案和预期答案。
- 留给评分者的答案、隐藏检查和其他运行结果。
- 为了让测试通过而额外塞进任务提示的规则。
- 另一版本的产物或作者逐步指导。

技能本身面向用户承诺的规则、定义和质量要求应在包中正常可读；“独立测试”不是把正常必需输入也删掉。修复对话类 Skill 若依任务就需要问题对话，提供合法的任务原始对话，但不提供 Skill 作者的开发讨论。

检查共享文件、默认记忆和宿主提示是否泄露开发资料。不能控制或观察全部隐含环境时，记录已隔离与未能核实的部分，采用可达到的最强隔离，不把程序性约定称为操作系统沙箱。

能用目录或权限隔离时采用适当隔离；只有提示级文件范围约束时如实说明。禁止读评分材料的要求不能弥补它们已经出现在提示里的泄漏。

## 选任务与对照

按目标使用场景选择正常任务、受影响的重要边界和必要恢复路径；不同 Skill 的覆盖范围不同，不规定统一题数。

- **开发任务：** 可以用于发现问题和修改，结果属于开发证据。
- **新任务：** 尚未用于修订说明，且在素材、结构、约束或关键取舍上有实质差异。
- **邻近不适用任务：** 用于检查误触发。
- **信息不足或工具失败任务：** 在这类情况确实影响目标能力时检查合理恢复和停止。

需要声称“有所改善”时，优先比较相同模型、档位、任务、工具、时间预算下的原包和改后包；新建技能可以与无 Skill 比较。没有对照时，可以说案例通过，不说证明了独立增益。已有可信的失败记录可作为诊断起点，但条件不一致时不能做严格因果对比。

不要只用文档里示例的换名版本。目标模型独立完成未见任务，可以提供有限的迁移证据，不证明全部任务可靠。

隐式触发与显式调用分开：把全文直接塞进上下文只能检查读后行为，不能证明宿主会自动发现和选择。宿主的发现/调用记录不可用时，保留该边界；名字和描述的分类检查不等于真实自动触发实测。

## 执行与修订

先固定旧版、新版或待测版本标识；可用现有提交、文件副本或内容摘要，不强制建立完整发布系统。让不同运行写到各自的空输出目录，避免继承答案或覆盖证据。

下面是可适配的执行委托结构；替换字段，不把评分者材料加入委托：

    请使用指定的完整技能包完成下述业务任务。
    技能包：本次允许读取的路径或附件
    任务：普通使用者的真实请求
    原始材料：本次业务输入
    输出位置：本次独立目录
    环境与边界：实际可用工具、允许的读写范围和副作用限制
    请提交实际成果；遇到缺失条件按技能处理，并记录实际障碍。
    不读取开发记录、其他运行产物或评分资料。

执行委托可规定输出路径和访问边界，不能替包补上如何解题。目标配置由真实宿主设置；写在委托中不等于完成配置。

执行期间不补答案。作者提示、用户纠正、手动修文件或额外重试都要保留记录。如果普通业务本来需要澄清，允许正常询问；区分用户补充业务输入与作者教授隐藏方法。

收回真实产物，检查必要工具是否真的运行、修改是否真的写入、成果是否可用。失败先按诊断参考查原因，修对应位置，再用新鲜执行上下文复测受影响行为。失败的任务已变成开发任务；需要迁移证据时另取未参与修订的任务。

不要求每个场景重复固定次数。重要结论、易波动行为或一次意外成功需要复测；有充分信息且未变化的检查可复用。没有新证据、失败或疑点，不无限重试到看见最好结果。

## 评审结果

直接事实用材料和产物核对。人工或模型评审关注完整成果，避免把工具调用、条目齐全和漂亮叙述当成实际效果。

对主观质量：
- 给明确参照和可观察维度，如信息是否讲清、视觉是否可读、动作因果是否成立。
- 比较版本时可隐藏版本身份、交换展示顺序，降低作者偏好和顺序影响。
- 不因结果更长就评分更高；也不通过强迫等长删掉必要内容。
- 用用户或领域读者的具体反馈校准。强模型评审可提供证据，不能冒充用户验收。

记录结论是通过、部分达到、失败或未验证，并说明依据。把评分表一项项填满不意味着质量真的达标；若评分遗漏用户目标，修正评分依据并解释，而不只是训练包去迎合题目。

## 证据与成本

每组实测保留：包版本、实际配置及其证据来源、可读材料范围、任务、输出位置、关键结果、失败、重试和作者辅助。普通小修可以在交付回复中记录，无需全部另建文件。

区分：
- 一次运行的时间与模型用量。
- 完成一份合格成果的累计重试、工具使用和人工返工。
- 方法开发或模型评审成本，与日常业务执行成本。

无法测得的值写未知，不用字符数猜 token，也不用想象的单价计算费用。小样本只报告实际案例数及条件，不外推出稳定成功率。完成格式检查不代表执行验证，独立读者理解不代表业务作品成功。

目标配置无法运行时，交付已改包和静态结果，清楚列出待验证任务与缺少的条件。不要为了把状态变成“通过”改用高成本模型自演；也不要因一个不可用的测试配置放弃已经能完成的改进。

## 何时需要重测

相关规则、参考资源、脚本、模型或环境发生变化时，选择受影响路径复测。若修改影响通用判断或入口，扩大到依赖它们的主要任务。单个错字或不影响行为的说明改动只需局部检查。

最终记录对应实际交付版本。若测试后又做了实质修改，原测试不能直接标成最终版本通过；说明可复用的范围并补相关检查。
