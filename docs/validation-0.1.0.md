## 运行配置与信息范围

行为验证的三个实际模型运行分别为：维护者一次、原包业务执行一次、改后包业务执行一次。三者均通过宿主子 Agent 调用请求 gpt-6.1-sol / medium，调用被接受；创建者没有用角色扮演模拟这些执行。README 阅读检查另有三次独立调用，请求同一模型与档位，不计作业务案例。

配置证据是明确的调用参数和成功返回的执行任务。未取得服务端响应中的模型标识，不能进一步证明内部路由。环境为同一 Windows Codex 宿主，允许普通本地文件工具，PowerShell 使用 pwsh。

每次均使用不继承父任务历史的调用设置：

| 角色 | 正常可读材料 | 没有在委托中提供的材料 |
| --- | --- | --- |
| 维护者 | Skill Improve 入口与运行参考、原技能、作者业务说明 | 业务测试输入、评分答案、其他执行结果、本包 docs/evals |
| 原包业务执行者 | 原技能、报名 JSON | 作者说明、维护对话、改后包、评分答案 |
| 改后包业务执行者 | 改后完整包、同一报名 JSON | 作者说明、维护记录、原包结果、评分答案 |

执行提示只给普通业务任务、文件位置和操作边界，没有额外传授计数方法。运行间没有作者提示或人工修改业务产物。

**隔离限制：** 各执行上下文不继承父任务聊天，但共享文件系统与正常宿主规则。读取范围由委托限制；维护者自报遵守了范围，没有对全部读取行为做独立访问审计。这是受约束的新上下文测试，不是操作系统权限隔离，也不能证明不存在所有隐含宿主影响。

协调者事先设计了测试输入与判定；维护执行者未获得业务测试输入。开发示例只有一个场次，业务输入增加了多个场次、截止后的乱序取消、同刻冲突、未知状态、缺失身份和容量。这里的“新任务”是相对于这次目标包改写而言，不是第三方密封基准。

## 观察到的改善

原包只说“按之前确定的口径处理重复和变更”。业务执行者发现关键口径不在包内，给出有假设标签的暂报，没有擅自将 held 换算为席位。它已正确处理多项通用问题；缺陷是无法给出需要领域定义才能确定的最终结论，不能描述成原包结果全部错误。

维护者从作者说明中恢复了截止、分组、冲突、状态和容量等规则，补充完整示例与事件回指。之后的新业务执行者得到：

| 场次 | 已确认 | 临时预留 | 候补 | 确定占用 | 容量判断 |
| --- | ---: | ---: | ---: | ---: | --- |
| A | 2 | 1 | 1 | 3 | 容量 3，已满 |
| B | 2 | 1 | 1 | 3 | 容量 2，超额 1 席 |
| C | 1 | 0 | 0 | 1 | 容量未知，无法判定 |

同刻冲突 E12/E13、身份缺失 E15、未知状态 E17 均列为待核实并排除于已确定计数；截止后的 E10/E16 被排除，恰好截止时刻的 E11 被保留。结果明确“仅基于已确定状态”，没有把剩余业务缺失假装已解决。事件回指可核对，建议没有写成已经通知或释放席位。

完整的 [复现步骤及实际产物](../evals/README.md) 随包保留，包含原包暂报和两次障碍记录。数字采用事先保存的判定核查；没有用篇幅、标题数量或步骤打勾代替成果判断。

## 失败、辅助与成本

- 原包的缺失口径保留在暂报和障碍记录中，未在同一次执行中给它补答案。
- 改后执行者自报一次本地 PowerShell 管道语法错误，随后自行修正并复算；这是同一次任务内的工具重试，未省略为“全程无错”。
- 没有重开业务执行直到抽到好结果；本轮每个版本各一次。维护者按自己的说明检查了教学示例，属于维护阶段自查。
- 作者辅助次数：独立业务执行中为零。必要的原始业务输入和维护阶段作者说明不算临时救场。
- 模型 token、精确运行时长与调用费用：未取得，不估算。创建者评审耗时未单独记录，未组织真人评审；未来用户返工成本尚未验证。只知道调用次数，不能据此证明总成本更低。
- 创建过程和文档检查属于开发成本，不等同于日常执行成本。

## 未验证范围

没有验证真实宿主的自动发现与隐式触发、全新机器安装、其他模型/档位/宿主、长期稳定性、创作或多媒体成果质量，也没有真实用户验收。相应要求已经写入流程，但“写入”不等于这些效果已经实测。

样本较小，只报告本次结果，不报告普遍成功率或低成本模型能完全复现高成本模型。当前案例公开后可做回归验证；后续若要确认迁移，应新增未用于修改的实质不同任务。改变相关核心规则、资源或执行配置后，补测受影响部分。
