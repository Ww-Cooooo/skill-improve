# 业务说明（虚构案例）

这是案例设计者提供给技能维护者的正常开发材料。以下业务约定是本案例的需求，不是行业通用规则；例子的预期结果也不代表真实用户验收。

目标：根据一份离线报名导出，给运营一份可核对的状态简报。不要发送通知或修改报名记录。保持原技能用途，不扩展成排班、营销或人员画像工具。

每条记录包含 event_id、participant_id、session_id、at、action，有时有 note。使用 JSON 中 cutoff 指定的截止时间，包含恰好等于 cutoff 的记录。晚于截止时间的记录不参与当期状态；记录排列顺序不是时间顺序。

按 participant_id 与 session_id 的组合确定一个人在一场活动的状态。取截止时间内最新记录。同一人跨场次独立处理，同一人同场的重复确认只算一个状态。若最新时间存在不同 action 的记录，不猜哪个优先：这组列为待核实，提供冲突 event_id，不纳入已确定的人数和席位占用。

action 的业务含义：
- confirmed：已确认，人数计 1，席位占用计 1。
- held：临时预留，预留人数计 1、席位占用计 1，但不计入已确认人数。
- waiting：候补人数计 1，不占席位。
- cancel：不计入当前已确认、预留或候补。
- 其他状态：标成待核实，不擅自归入上述类别。
缺少必要身份或时间字段的记录列为待核实，不把缺失身份的记录合并成同一个人。

风险按已确定的席位占用 confirmed + held 与 capacity 比较：大于容量是超额，等于容量是已满，小于容量是有余位。容量缺失时明确无法判定容量状态，不能填一个猜测值。存在待核实记录时，说明结论只基于已确定状态，不声称全部数据已核清。

每场活动输出已确认、临时预留、候补、确定席位占用和容量状态，回指产生当前状态的 event_id。另列待核实和被截止时间排除的记录。将事实与建议分开；有候补且已满或超额时可建议运营核查预留，不得自行通知或释放席位。备注中的口头估计不能覆盖结构化事件状态。

开发时有人说“汇报简单点”，指面向运营的结果，不要求把这个技能文件压成几句话。

方法核对示例：
场次 T 容量 2，截止 2026-04-01T18:00:00Z；U1 在 10:00 confirmed、12:00 cancel，U2 在 11:00 confirmed，U3 在 13:00 held。
按本案例定义，当前已确认 1、预留 1、候补 0、占用 2，场次已满。没有真实模型独立执行证据时，应如实说明。
